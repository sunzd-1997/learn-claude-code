# Codex 初次使用指南

这份文档给第一次使用 Codex 的开发者准备，目标是回答两个问题：

1. Codex 应该怎么用。
2. 为什么它和 Cursor 这类 IDE 型 AI 工具不太一样。

---

## 先建立正确心智

Codex 更像一个运行在当前工作区里的工程代理，而不是传统意义上的“带 AI 的编辑器”。

你可以把两者简单区分为：

- Cursor：以 IDE 为中心，你主导编辑，AI 深度辅助。
- Codex：以任务执行为中心，你下达目标，AI 进入工作区读代码、改代码、跑命令、汇报结果。

所以在 Codex 里，核心不是“打开某个文件”，而是下面这件事是否成立：

- 当前线程是否已经绑定到一个项目目录。

如果已经绑定，Codex 就可以直接在这个目录里工作。它会把这个目录视为当前工作区，再根据你的要求去扫描、修改、验证。

---

## 为什么它看起来不像 Cursor 那样“直接打开项目”

这是正常现象，不是你操作错了。

Cursor 的主交互入口是 IDE 文件树、编辑器标签页、代码补全和内联修改；Codex 的主交互入口是工作区、终端能力、文件读写和任务执行。

因此 Codex 更常见的起手方式不是：

- 我打开一个文件，然后让 AI 看着我写。

而是：

- 我进入一个工作区。
- 我告诉它先读什么、查什么、改什么。
- 它自己去执行，再把结果反馈给我。

换句话说，Codex 不一定强调“直接打开项目”的视觉动作，但它强调“是否已经进入这个项目对应的工作区”。

---

## 在 Codex 里，你最常做的几类事

- 让它先梳理项目结构。
- 让它找到某个功能、接口、模块的实现位置。
- 让它直接修改代码。
- 让它排查报错、补测试、跑命令。
- 让它 review 改动，重点找 bug 和回归风险。
- 让它基于约束持续执行到完成。

这类任务比“陪写型”交互更适合 Codex。

---

## 最推荐的提问方式

第一次用时，不要只说“帮我看看这个项目”，而要尽量把任务讲清楚。

一个好用的请求通常包含 4 个元素：

- 目标：你想解决什么问题。
- 范围：允许改哪里，不允许改哪里。
- 约束：例如不改接口、不新增依赖、不动数据库。
- 验证：要不要跑测试、构建、lint。

例如：

```text
先扫描这个项目，告诉我技术栈、启动方式和关键目录。
```

```text
帮我找到登录接口的实现位置，并解释调用链路。
```

```text
修复这个报错，只改后端鉴权模块；改完跑相关测试，并告诉我根因。
```

```text
review 一下这次改动，重点看 bug、行为回归和缺少的测试。
```

## 一个通用的新项目上手流程

进入一个新仓库后，可以直接按这个顺序让 Codex 工作：

1. 先扫描项目，说明技术栈、目录结构、启动命令。
2. 再定位核心入口文件和主要模块关系。
3. 然后开始实现或修改具体需求。
4. 改完后跑相关测试或构建。
5. 最后输出一份简短变更说明。

对应的可直接复用提示词：

```text
先扫描这个项目，告诉我：
1. 技术栈
2. 目录结构
3. 启动方式
4. 关键入口文件
5. 推荐阅读顺序
```

```text
接下来帮我实现 XXX。
要求：
1. 只改 XXX 模块
2. 不改对外接口
3. 改完跑相关测试
4. 最后给我简短说明
```

---

## 什么时候让它“先解释”，什么时候让它“直接改”

适合先解释的情况：

- 你还不熟悉项目。
- 你不确定改动范围。
- 你先想看方案、风险和定位。

适合直接改的情况：

- 目标明确。
- 范围明确。
- 约束明确。
- 你希望它直接执行，不要只停留在分析。

两种说法差别很大：

```text
先不要改代码，先解释这个模块的结构和调用关系。
```

```text
直接修复这个问题，必要时自行查找相关代码并验证。
```

## 和 Cursor 的核心区别

最重要的区别有这几条：

- Cursor 更偏“编辑器协作”。
- Codex 更偏“工作区代理执行”。
- Cursor 更适合边写边补全、边选中边改。
- Codex 更适合把一段完整工作交给它完成。
- Cursor 的文件打开感更强。
- Codex 的工作区、命令执行、结果汇报感更强。

所以如果你以前主要用 Cursor，迁移到 Codex 时最需要调整的是操作习惯：

- 少一点“我打开文件给你看”。
- 多一点“你先去扫描并定位，然后直接处理”。

---

## 让 Codex 更好用的几个原则

### 1. 任务要具体

比起：

```text
帮我优化一下这里。
```

更推荐：

```text
帮我优化这个接口的超时问题，优先减少重复请求，不要改返回结构。
```

### 2. 明确边界

常见边界包括：

- 只改前端 / 只改后端
- 不改数据库 schema
- 不新增第三方依赖
- 保持现有 API 不变
- 只做最小修复

### 3. 明确你是否要验证

如果你希望它不仅改代码，还顺手验证，最好明确说：

- 跑测试
- 跑构建
- 跑 lint
- 告诉我有没有失败项

### 4. 明确你想要什么输出

常见输出形式：

- 先解释
- 直接修改
- 给排查结论
- 给 review findings
- 给上手说明

---

## 这类话术通常最好用

适合新手的高频模板：

```text
先帮我梳理这个项目的结构和启动方式。
```

```text
先告诉我这个项目的核心代码在哪，推荐我从哪几个文件开始读。
```

```text
帮我找到 XXX 功能的入口和调用链路。
```

```text
帮我实现 XXX，限制只改 XXX 目录，改完做基本验证。
```

```text
帮我 review 当前改动，重点看 bug、回归风险和缺少的测试。
```

## 对这个仓库来说，应该怎么开始

当前仓库 `learn-claude-code` 的结构很清晰，适合把 Codex 当作“项目导览 + 改动执行器”来用。

### 仓库主要组成

- `agents/`：核心教学代码，按 `s01` 到 `s12` 递进。
- `agents/s_full.py`：把完整机制合在一起的总纲版本。
- `docs/zh/`：中文文档。
- `web/`：Next.js 文档站。
- `requirements.txt`：Python 依赖。
- `.env.example`：模型和 API 配置示例。

### 推荐阅读顺序

如果你想理解“一个类 Claude Code 的 agent 是怎么长出来的”，推荐顺序是：

1. `README-zh.md`
2. `agents/s01_agent_loop.py`
3. `agents/s02_tool_use.py`
4. `agents/s03_todo_write.py`
5. 按顺序读到 `agents/s12_worktree_task_isolation.py`
6. 最后再看 `agents/s_full.py`

### 常用启动命令

Python 部分：

```bash
pip install -r requirements.txt
python agents/s01_agent_loop.py
python agents/s12_worktree_task_isolation.py
python agents/s_full.py
```

文档站：

```bash
cd web
npm install
npm run dev
```

### 配置准备

复制 `.env.example` 到 `.env` 后，至少需要配置：

- `ANTHROPIC_API_KEY`
- `MODEL_ID`

如果你使用兼容 Anthropic API 的其他提供商，也可以配置：

- `ANTHROPIC_BASE_URL`

## 一句话总结

如果你觉得 Codex “不像 Cursor 那样直接打开项目”，本质上是因为它的设计重点不是“IDE 内联交互”，而是“在当前工作区里接任务并执行”。

最自然的用法不是“我打开文件给你看”，而是“你先进项目、理解结构、然后直接帮我完成一段工作”。
